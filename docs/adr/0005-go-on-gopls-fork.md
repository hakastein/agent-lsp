# Go: форк gopls и кэш пользователя в SQLite

Здесь решено, откуда берутся ответы о Go-коде, где лежит то, что для них посчитано, и когда оно считается заново.

## Ответы — форк внутренних пакетов gopls

- Пакет `golang` вызывает функции gopls (`golang.Definition`, `golang.References`, `golang.Implementation`,
  `golang.Rename`, индекс символов `Snapshot.Symbols`) напрямую: сессия,
  представление (view) и снимок gopls живут в процессе программы, протокола LSP и сервера нет.
- Внутренние пакеты gopls из модуля не импортируются, поэтому они скопированы в `internal/gopls` вместе с нужными им
  внутренними пакетами `golang.org/x/tools` (BSD-3, уведомление авторов сохранено). Версия upstream, раскладка и
  каждая правка записаны в [`internal/gopls/FORK.md`](../../internal/gopls/FORK.md); upstream подтягивается вручную по
  этому списку.
- В форке только замыкание того, что вызывает `golang`: без протокола LSP, анализаторов, staticcheck и запуска
  govulncheck; из `vulncheck` — только типы результатов, которые импортирует `cache`. Остальные публичные пакеты
  `x/tools` — зависимость `go.mod`.
- Корень — каталог с `go.mod` или `go.work`; представление gopls строится для него так же, как для папки редактора.
- `Definition`, `Symbols` и `Outline` дополняют ответ сигнатурой, докблоком и диапазоном объявления по синтаксическому
  дереву файла объявления (`go/parser`); `Outline` читает только синтаксис файла.

Причина: gopls уже разрешает Go по типам, включая стандартную библиотеку, зависимости, встраивание и дженерики; свой
резолвер повторял бы его хуже. Форк, а не процесс gopls: программа остаётся одним бинарником без подпроцессов-серверов.

## Платформы: linux, darwin, windows

- Пакеты корня загружаются под каждую из GOOS linux, darwin и windows: на платформу — своя сессия gopls с одним
  представлением, `GOOS` которого задан в `Options.Env` и в `GoEnv` (`go env` спрашивается один раз), и свой загрузчик
  пакетов (ключ загрузки уже содержит `GOOS`). Сессии делят один `cache.Cache` — его gopls и задумал общим для сессий.
  Одна сессия с тремя представлениями одного каталога невозможна: gopls отвечает `ErrViewExists`. Представления
  загружаются разом. `GOOS` окружения процесса не участвует: ответ одинаков на любой машине; `GOARCH` — из окружения.
- `Definition` отвечает по первой платформе, которая собирает файл вопроса; `Symbols` ищет в пакетах всех трёх.
  `.go`-файл, который не собирает ни одна, — ошибка вопроса: по нему нечего разрешать.
- `References` — объединение ответов платформ: платформу, которая собирает файл вопроса, `golang.References`
  спрашивает в месте вопроса; другую — в её собственном объявлении того же символа, если оно у неё есть. Символ пакета
  платформы сопоставляют по пакету, типу, в котором он объявлен (у метода и поля), и имени; локальный символ живёт
  только в файле вопроса. Объявление не использование. Одинаковые места сливаются, места идут по файлам, строкам и
  колонкам.
- Реализации — `golang.Implementation`, только когда символ — интерфейсный тип или метод интерфейса: тогда gopls ищет
  подтипы. Для конкретного типа или метода gopls ищет надтипы (интерфейсы, которые тот реализует), а это не реализации
  символа: список пуст.
- Неразрешённых мест у Go нет: gopls разрешает по типам каждый идентификатор пакетов трёх платформ. Файлы под другой
  `GOOS`, `GOARCH` окружения или тегом сборки не загружаются и в ответ не попадают.
- Символ, объявленный для платформ по отдельности (`f` в `f_unix.go` и в `f_windows.go`, метод или поле такого типа),
  — один символ: вопрос на любом из объявлений находит использования всех, `Rename` переименовывает все объявления.
  Иначе переименование одной копии ломало бы сборку под другую ОС. Поле или метод типа без имени на уровне пакета
  (`var cfg struct{ n int }` в `x_unix.go` и в `x_windows.go`) по пакету, типу и имени не найти: такой символ
  находят только платформы, которые собирают файл вопроса.

Причина: файлы под ограничениями сборки (`_windows.go`, `_darwin.go`) иначе не видны ни одному ответу. Цена — три
загрузки пакетов вместо одной; они идут параллельно, и повторный вызов на `golang.org/x/tools` укладывается в десятые
доли секунды (замеры — в README).

## Переименование

- `Rename` — объединение ответов `golang.Rename` по платформам, спрошенных в тех же местах, что и у `References`.
  Одинаковые правки сливаются. Правки идут по файлам, строкам и колонкам. На диск `Rename` ничего не пишет.
- Метод интерфейса: `golang.Rename` переименовывает вместе с ним методы типов, которые код присваивает интерфейсу, и
  только их. Тип, который реализует интерфейс по набору методов, но интерфейсу не присвоен, свой метод сохраняет:
  совпадение имени и сигнатуры не говорит, что тип служит этому интерфейсу, а переименование такого метода ломало бы
  другие интерфейсы, которым тип служит (`String` и `fmt.Stringer`).
- Связанный метод в пакете, который переименование не правит (тип стандартной библиотеки или зависимости, присвоенный
  интерфейсу корня; тип пакета, который пакет интерфейса импортирует), upstream оставил бы со старым именем, и код не
  собрался бы. Форк отказывает в `renameExported` с местом этого метода.
- Конкретный метод `String() string`, `Error() string` или `Format(fmt.State, rune)` не переименовывается ни сам, ни
  вместе с методом интерфейса: `fmt` находит его через `any`, а не через присваивание, которое видит gopls. Тип без него
  печатается иначе, и `go vet` падает на `%s` и других глаголах, которые он обслуживал. Форк отказывает в
  `checkMethod` с местом метода.
- Отказ — ошибка с местом: объявление вне корня (`Origin` не корень: std, module, vendor) — место объявления;
  конфликт имени — места из проверки gopls, с полными путями; связанный метод вне переименования — его место; поле
  или метод типа без имени на уровне пакета, если файл вопроса собирают не все платформы, — место вопроса: другие
  платформы оставили бы своим копиям старое имя. Пакет (его объявление `package` или имя импорта) —
  `ErrNotSupported`. Место без символа — пустой ответ, как у остальных операций.
- Файлы, которые не собирает ни одна из трёх платформ (другая `GOOS`, `//go:build ignore`), не правятся.

Причина: ответ потребитель проверяет и пишет сам; правки, которые собраны со всех платформ, держат сборку под
каждой.

## Кэш пользователя

- Всё посчитанное лежит в одной базе SQLite пользователя `<os.UserCacheDir()>/agent-lsp/cache.sqlite`
  (`modernc.org/sqlite`). Открывает её и чистит `internal/cachedb`; таблицы Go — с префиксом и номером схемы
  (`go1_…`). Несовместимое изменение таблиц — новый номер и новые таблицы. Таблицы PHP (`php1_…`) лежат в той же
  базе (ADR 0001).
- Файл базы, который не база SQLite или повреждён (`SQLITE_NOTADB`, `SQLITE_CORRUPT` от схемы или чистки),
  `Open` удаляет вместе с `-wal` и `-shm` и создаёт заново пустым: это переиндексация, в базе только то, что можно
  посчитать снова. Не удалось удалить (на windows базу держит открытой другой процесс) — ошибка `Open` с путём файла.
  Другая ошибка открытия (права, блокировка) — тоже ошибка `Open`.
- Порча, найденная позже (загрузкой пакетов, в том числе в `Open`, записью кэша gopls в `Close`), — ошибка SQLite
  этого вызова с путём файла базы; её не обрабатывают: файл удаляет человек, следующий вызов индексирует заново.
  Неудачное чтение кэша gopls — промах. Сама база не ломается: WAL с `synchronous=NORMAL` и транзакции атомарны при
  падении процесса, порча бывает только извне. Проверки всей базы при открытии нет: она стоила бы каждому вызову.
- Открытие, создание схемы, чистка и пересоздание базы идут под межпроцессной блокировкой файла `cache.sqlite.lock`
  рядом с ней (`flock` на linux и darwin, `LockFileEx` на windows): процессы, стартовавшие разом на отсутствующей или
  битой базе, открывают её по очереди и все успевают.
- Строка таблицы с столбцом `used` (unix-время последнего использования) удаляется, если её не использовали 14 дней.
  Чистит `Open` попутно, не чаще раза в сутки; чтение обновляет `used`, когда оно старше часа (кэш gopls) или суток
  (загрузки пакетов).
- `go1_blobs` — кэш gopls (`filecache`: export data, индексы ссылок, наборов методов, символов, typerefs). Ключ gopls
  — хеш входов: пути и содержимое файлов пакета, ключи зависимостей, размеры типов, версия Go модуля. Ключ строки —
  хеш соли и ключа gopls; соль — номер схемы, версия форка и версия Go, которой собран бинарник (её `go/types`
  проверяет типы). Значение, записанное другой сборкой, не читается.
- Значения копятся в памяти и пишутся одной транзакцией на `Close`: запись на каждое значение стоила бы больше, чем
  сам ответ.
- `go1_loads` — ответ `go list` (через `go/packages`) по ключу конфигурации загрузки: каталог, шаблоны, режим,
  переменные окружения `GO*` и `CGO_*`, содержимое файла настроек `go env -w` (`GOENV`), флаги сборки, `go version`,
  `GOROOT`, `GOOS`/`GOARCH`. Ответ хранит состояние файлов, из которого посчитан; при том же состоянии `go list` не
  запускается.
- Состояние файлов — хеш `go.mod`, `go.sum`, `go.work`, `go.work.sum`, `vendor/modules.txt` и заголовков всех
  `.go`-файлов (ограничения сборки, имя пакета, импорты) под корнем и под каталогами, которые `go.mod`/`go.work`
  корня подключают через `replace` и `use`. Обход повторяет `go list ./...`: каталоги `testdata`, `.*` и `_*`
  пропускаются; корень-симлинк обходится через ссылку. Заголовок файла хранится в `go1_files` с размером и временем
  изменения; файл с теми же размером и временем не перечитывается. Обход отмечает строки каталога использованными.
- Правка тела функции, комментария или нового объявления не меняет состояние: загрузка пакетов переиспользуется, а
  gopls сам читает изменённый файл и пересчитывает затронутые пакеты по ключам кэша. Новый или удалённый файл,
  изменённый импорт, `go.mod`, `go.sum` или `go.work` — новая загрузка.
- Восстановленная загрузка не используется, если файла из кэша сборки Go (`GOCACHE`), на который она ссылается, уже
  нет.

Причина: каждый вызов программы — новый процесс. Без базы каждый вызов платил бы `go list` всего модуля и проверку
типов всех зависимостей; с ней повторный вызов на `golang.org/x/tools` укладывается в десятые доли секунды (замеры —
в README).

## Worktree

- Два worktree одного модуля делят строки кэша всего, что лежит вне их: стандартной библиотеки и модулей из кэша
  модулей — пути этих файлов совпадают.
- Пакеты самого worktree каждый считает сам: ключи gopls содержат пути файлов, а export data — позиции с путями.
  Общая строка дала бы ответ с путём другого worktree.
- Загрузка пакетов хранится на каталог корня: новый worktree запускает `go list` один раз.

## Процесс

- `Open` проверяет корень, открывает базу, спрашивает `go env` и `go version`, создаёт по сессии gopls на платформу
  и ждёт загрузки пакетов всех трёх. В процессе одновременно открыт один Go-индекс: кэш gopls глобален для процесса;
  второй `Open` до `Close` первого — ошибка.
- Ответы — по файлам на диске; правку, сделанную после `Open`, гарантированно видит следующий `Open`. Позиция
  проверяется по правилам, общим для языков (`internal/position`).
- Пути файлов корня в ответах начинаются с корня в том виде, в каком его получил `Open` (абсолютный путь, символические
  ссылки не раскрываются), как в PHP: корень, открытый через ссылку, отвечает путями через неё, и позиции задаются
  такими же путями.
- Повторный `Close` ничего не делает.
- Строки `go: packages loaded: N`, `go: packages reused: N` (`N` — пакеты, которые вернула загрузка) и
  `go: cache: R reused, M missed, W written` в функции диагностики — диагностика, не контракт.
